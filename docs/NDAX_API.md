# NDAX API Reference (Retail Canadian Platform)

This document records what was verified about the **retail Canadian NDAX**
trading API (`ndax.io`, pairs such as `BTC/CAD`) as of **2026-08-29**, and how
the NDAX adapter implements it. Update this file whenever a ⚠️/🔎 item is
empirically confirmed or refuted.

**Critical context — there are two DIFFERENT "NDAX" API families:**

| Platform | Docs | Auth model | Pairs |
| --- | --- | --- | --- |
| **Retail Canadian** `ndax.io` | `apidoc.ndax.io`, `github.com/NDAXlO/ndax-api-documentation`, `ndaxlo.github.io/API` | WS `AuthenticateUser` (APIKey/Secret/UserId/Nonce) | BTC/CAD, ETH/CAD, ... |
| **B2B/institutional** `docs.ndax.in` | `docs.ndax.in/v3`, FIX protocol | REST headers `X-NDAX-API-KEY`/`X-NDAX-SIGNED`/`X-NDAX-TIMESTAMP`/`X-NDAX-PASSPHRASE` | e₹-crypto (Indian CBDC) |

> **This project targets the retail Canadian platform (`BTC/CAD`).** The
> `docs.ndax.in/v3` REST signing headers belong to a *different* institutional
> platform and must NOT be conflated with the retail API.

**Live-verified 2026-08-28:** `Ping`, `GetInstruments`, `GetProducts`,
`GetLevel1`, `GetL2Snapshot`, and `GetTickerHistory` were exercised directly
against `https://api.ndax.io:8443/AP` (read-only, no credentials). Exact wire
shapes below folded back into the adapter.

Conventions used below: **✅ CONFIRMED** (in NDAX official docs/support),
**🔎 CORROBORATED** (not in official docs, but verified against the production
CCXT `ndax.ts` connector — lines referenced below follow that source),
**⚠️ VERIFY** (ambiguous / no source — must be checked against the live API),
**❌ UNSUPPORTED / NOT FOUND**.

> Phase 4 (2026-08-28): most previously-flagged items were resolved by reading
> the live, production-proven CCXT connector implementation (and Hummingbot).
> The adapter was realigned to that behavior.

## 1. Base URLs

**WebSocket gateway (authentication is WS-only):**

| Item | Value | Source |
| --- | --- | --- |
| ✅ WebSocket endpoint | `wss://api.ndax.io/WSGateway/` | apidoc.ndax.io (§AuthenticateUser), NDAXlO GitHub README |
| 🔎 REST API base URL (public & private) | `https://api.ndax.io:8443/AP` | **NOT in apidoc.ndax.io.** CCXT `urls.api.public/private` + Hummingbot. |
| 🔎 Test/staging REST host | `https://ndaxmarginstaging.cdnhop.net:8443/AP` | CCXT `urls.test`. |

> The official v3.3 doc never documents a REST base URL (it only documents the
> WebSocket gateway), but CCXT ships this URL against production NDAX and it is
> used in the wild; treat it as the rest of the industry does.

## 2. Message framing (WebSocket)

All WS messages are wrapped in a JSON frame:

```json
{ "m": 0, "i": 2, "n": "GetLevel1", "o": "{\"OMSId\":1,\"InstrumentId\":1}" }
```

| Key | Meaning |
| --- | --- |
| `m` | 0 request, 1 reply, 2 subscribe, 3 event, 4 unsubscribe, 5 error |
| `i` | sequence number (non-zero, client uses even numbers starting at 2) |
| `n` | function name (the "endpoint") |
| `o` | JSON-stringified payload |

✅ Confirmed in apidoc.ndax.io and NDAXlO GitHub README.

## 3. Authentication

⚠️ **The retail API auth model is WebSocket-based and uses four values, not a
simple key/secret pair:**

```
APIKey        — AlphaPoint-generated public key
API Secret    — shared secret (HMAC key)
UserId        — numeric user id
Nonce         — per-request value (typically epoch ms)
```

### AuthenticateUser (WS-only)

```json
{
  "APIKey": "…",
  "Signature": "…",
  "UserId": "96",
  "Nonce": "2247733562"
}
```

- ✅ Endpoint exists; payload structure confirmed (apidoc.ndax.io + NDAXlO repo).
- ✅ **WS-only:** "AuthenticateUser is a WebSocket call… It cannot be used over
  HTTP: … the HTTP path returns `{"Authenticated": false}`."
- ✅ Response includes `user`, `authenticated`, `locked`, `requires2FA`,
  `twoFAType`, `twoFAToken`.

### Signature algorithm — 🔎 CORROBORATED

The official docs only say Signature is "a long alphanumeric string generated by
AlphaPoint by using the APIKey and Nonce." **The algorithm is not specified.**

Third-party implementations (ndaxrs, Hummingbot, CCXT) all agree on:

```
signature = lowercase-hex( HMAC-SHA256( key = apiSecret,
                                        msg = nonce + userId + apiKey ) )
```

(concatenation with no separators; `nonce` = epoch ms). CCXT `sign()` (lines
2712–2764) computes `hmac(sha256, nonce + uid + apiKey, secret)`, confirming the
algorithm and the exact concatenation. `src/exchanges/ndax/signing.ts` matches it.

### Private REST auth — 🔎 CORROBORATED (two modes, CCXT `sign()`)

1. **Per-request header signing** (no session token). Every private request
   carries HTTP headers:
   ```
   Nonce:     <epoch ms, monotonic>
   APIKey:    <api key>
   Signature: lowercase-hex HMAC-SHA256(secret, nonce+userId+apiKey)
   UserId:    <numeric user id>
   ```
   This is CCXT's pre-`signIn` path and works for reads. The adapter uses this
   mode (`src/exchanges/ndax/NdaxAdapter.ts`), requiring only APIKey/Secret/UserId.
2. **Session-token mode** (`signIn`): `Authenticate` (public, **HTTP Basic auth**
   header `login:password`) → `SessionToken` or `Pending2FaToken`; 2FA via
   `Authenticate2FA` (header `Pending2FaToken` + TOTP); afterwards requests carry
   `APToken: <SessionToken>`. Requires the account email/password (+2FA). Not
   needed for the read-only milestone.

⚠️ Verified only against third-party sources, not against a live NDAX account.
Authenticated reads remain gated (`ENABLE_AUTHENTICATED_READS=false` default).

## 4. Public market-data calls

All ✅ from apidoc.ndax.io unless noted.

### GetLevel1 (ticker / last price)

Request `{ "OMSId":1, "InstrumentId":1 }`. Response fields include `bestBid`,
`bestOffer`, `lastTradedPx`, `lastTradedVolume`, `lastTradeTime`,
`sessionOpen/High/Low/Close`, `currentDayVolume`, `rolling24HrVolume`, etc.

### GetL2Snapshot (order book)

Request `{ "OMSId":1, "InstrumentId":1, "Depth":100 }` (Depth defaults to 100).
Response is an array of arrays:

```text
[MDUpdateId, AccountId, ActionDateTime(ms POSIX), ActionType,
 LastTradePrice, OrderId, Price, ProductPairCode, Quantity, Side]
```

`Side`: 0 Buy, 1 Sell, 2 Short(reserved), 3 Unknown.

✅ Live-verified row indices (2026-08-28): **Price = index 6, Quantity = index
8, Side = index 9** (0 = bid, non-zero (1) = ask).

### Precision caveat (✅ live-verified)

NDAX public JSON carries prices/quantities as plain JSON numbers, which are
IEEE-754 doubles. For a price like `108200` this is exact; for very small
quantities (e.g. `0.00000001`) the wire may show `1e-8`, and high-precision
values (e.g. `CurrentDayVolume: 0.0247040600000000000000000000`) are emitted
**as strings** by the platform. The adapter renders numbers via `toFixed(8)`
before parsing into scale-8 `Money`. This rounds to 8 decimals (the platform's
max precision), so it is exact for everything NDAX can actually represent.

### GetTickerHistory — CANDLES/OHLCV ✅ (live-verified format + time)

✅ Verified 2026-08-28:

- `FromDate`/`ToDate` MUST be **`"YYYY-MM-DD HH:MM:SS"` UTC** (space
  separator) — this exact format was accepted live.
- `Interval` = seconds (60, 300, …) → 1m/5m/… candles.
- Row format `[DateTime, High, Low, Open, Close, Volume, InsideBid, InsideAsk,
  InstrumentId, StartTime]` — **`DateTime[0]` is the candle END time**;
  `StartTime[9]` (epoch ms) is the candle START/open time. The adapter keeps
  `DateTime[0]` as `Candle.timestampMs` (matches CCXT `parseOHLCV`), so on a
  thin/low-turnover market the final candle may be open-ended.
- Sparse data: candles are **returned for intervals with no trades only when
  activity is present**; a quiet market returns fewer rows than the requested
  window (e.g. 25 rows over 2 hours of 5m candles). Callers must tolerate gaps.

### GetProducts (assets)

Request `{ "OMSId":1 }`. Response: array of `{ omsId, productId, product,
productFullName, productType, decimalPlaces, tickSize, noFees }`. `productType`:
0 Unknown, 1 NationalCurrency, 2 CryptoCurrency, 3 Contract. `decimalPlaces` max 8.

### GetInstruments / GetInstrument (markets)

Request for GetInstruments `{ "OMSId":1 }`. Response: array of instruments:

```json
{ "omsId":1, "instrumentId":3, "symbol":"BTCCAD", "product1":…,
  "product1Symbol":"BTC", "product2":…, "product2Symbol":"CAD",
  "instrumentType":…, "venueInstrumentId":…, "venueId":…,
  "sessionStatus":…, "quantityIncrement":…, "priceIncrement":… }
```

- ✅ `symbol` is BASE+QUOTE concatenated (e.g. `BTCUSD`, `BTCCAD`).
- ✅ `instrumentId` (numeric) is what all other calls require.
- ✅ `quantityIncrement` / `priceIncrement` = the tick/step increments.
- 🔎 **`MinimumQuantity`, `MinimumPrice`** — present in live data (✅ verified
  2026-08-28; e.g. BTCCAD `MinimumQuantity = 0.00001`, `MinimumPrice = 25000`).
  They arrive as JSON **numbers** (may be scientific-notation floats,
  `QuantityIncrement: 1e-8`) — parsed via `Money` scale-8 (numbers rendered
  with `toFixed(8)` before parse). **Important:** `MinimumPrice` is a
  per-instrument **price FLOOR** (e.g. 25000 for BTCCAD), NOT a minimum order
  notional — the adapter deliberately does NOT map it to `MarketInfo.minOrderQuote`
  (that field is reserved for a true minimum-order-value rule). Response keys are
  **capitalized camelCase** (`MinimumQuantity`, not `minimumQuantity`);
  `Symbol` = `"BTCCAD"` (base+quote, no slash).

> Important: public reads (`GetLevel1`, `GetL2Snapshot`, `GetTickerHistory`,
> `GetInstruments`, `Ping`) are **GET** with url-encoded query params and need
> **no auth** (CCXT treats them as public). Only private reads use the signed
> headers above.

### GetTickerHistory — CANDLES/OHLCV ✅

Historical OHLCV-style data is available:

```json
{ "InstrumentId":1, "Interval":60, "FromDate":"2018-07-18",
  "ToDate":"2018-07-19", "OMSId":1 }
```

- `Interval` = seconds between ticks (60s, 300s, 900s… map to 1m/5m/15m…).
- Response: array of arrays `[DateTime(ms POSIX), High, Low, Open, Close, Volume,
  InsideBid, InsideAsk, InstrumentId]`, oldest first.

⚠️ **Resolved (Phase 4):** the request table says "Microsoft Ticks format" but
the live connector (CCXT `fetchOHLCV`, lines 979–1018) sends
`FromDate`/`ToDate` as **`"YYYY-MM-DD HH:MM:SS"` space-separated UTC** (CCXT
`ymdhms`) — NOT ISO-8601 with a `T`, and NOT ticks. Example:
`FromDate=2026-08-28 12:00:00`. The adapter formats with `ymdhms()` in
`src/exchanges/ndax/mappings.ts`. `Interval` is sent as a number (60, 300, …).

### Other public calls
✅ `Ping` (health); `GetEarliestTickTime`. CMC-style endpoints (`Ticker`,
`OrderBook`, `Trades`, `Summary`, `Assets`) exist in the doc but with **no URL
given** ⚠️.

## 5. Private (authenticated) account reads

All ✅ from apidoc.ndax.io.

- **GetUserAccounts** `{ omsId, userId, userName }` → response is a **flat list of
  integer account ids** (e.g. `[449]`), not objects. `userName` is the account
  login email (CCXT requires it); the adapter passes it if configured.
- **GetAccountPositions** (balances) `{ omsId, AccountId }` → per asset:
  `ProductSymbol` (e.g. "BTC"), `ProductId`, `Amount` (total), `Hold`
  (unavailable); available = Amount − Hold. Capitalized camelCase keys.
- **GetOpenOrders** `{ omsId, AccountId, InstrumentId? }` → array of orders (or
  empty array). Order object has `Side` ("Buy"/"Sell"), `OrderId`, `Price`,
  `Quantity`, `DisplayQuantity`, `Instrument` (numeric id), `Account`,
  `OrderType` ("Limit"/"Market"), `ClientOrderId`, `OrderState` (string),
  `ReceiveTime`, `OrigQuantity`, `QuantityExecuted`, `AvgPrice`, `…`.
- **GetOrderHistory** `{ omsId, AccountId }` → all orders (open + executed).
- **GetOrdersHistory** `{ omsId, accountId, clientOrderId, instrumentId,
  startTimestamp, endTimestamp, depth, startIndex, … }` → paginated, POSIX times.
- **GetOrderStatus** `{ omsId, AccountId, OrderId }` → order object array.
- **GetAccountTrades** (fills) `{ OMSId, AccountId, StartIndex, Count }` → up to
  200 trades with `price, quantity, value, fee, feeProductId, side, tradeTime…`.
- **GetOrderFee** `{ omsId, accountId, instrumentId, productId, amount, price,
  orderType, makerTaker, side }` → `{ OrderFee, ProductId }` (fee ≥ 0.01).

> Private reads are **GET** with these params url-encoded (CCXT
> `privateGetGetUserAccounts` etc.) plus the signed headers above. Mutations
> (`SendOrder`, `CancelOrder`, …) are **POST** with a JSON body.

## 6. Order management

> Re-verified against the current official apidoc.ndax.io (v3.3) on
> **2026-08-29**. Status labels: ✅ CONFIRMED in official doc, 🔎 CORROBORATED
> (CCXT connector), ⚠️ VERIFY (ambiguous / not yet live-tested).

### SendOrder — POST (mutation, JSON body) — ✅

**Endpoint:** `POST https://api.ndax.io:8443/AP/SendOrder` (private, signed).
**Call Type: ASYNCHRONOUS** (✅ "Note: Call Type is asynchronous") — the response
only records whether the request was *accepted*, NOT that the order is on the
book. Always reconcile via `GetOrderStatus`/`GetOpenOrders` to confirm.

✅ Documented request (v3.3, note `quantity` is **lowercase** in the example,
lower still appears in the field table as `Quantity` — see caveat below):

```json
{ "InstrumentId":1, "OMSId":1, "AccountId":1, "TimeInForce":1,
  "ClientOrderId":1, "OrderIdOCO":0, "UseDisplayQuantity":false,
  "Side":0, "quantity":1, "OrderType":2, "PegPriceType":3, "LimitPrice":8800 }
```

✅ Documented response (only acknowledgement):

```json
{ "status":"Accepted", "errormsg":"", "OrderId":123 }
```

`status` = `"Accepted"`/`"Rejected"` (string). `OrderId` = server order id.

✅ Enum values (documented):
  - **Side:** 0 Buy, 1 Sell, 2 Short, 3 Unknown; **OrderType:** 0 Unknown, 1
    Market, 2 Limit, 3 StopMarket, 4 StopLimit, 5 TrailingStopMarket, 6
    TrailingStopLimit, 7 BlockTrade; **TimeInForce:** 0 Unknown, 1 GTC (default),
    2 OPG, 3 IOC, 4 FOK, 5 GTX, 6 GTD; **PegPriceType:** 1 Last, 2 Bid, 3 Ask,
    4 Midpoint.

✅ **`ClientOrderId` is a LONG INTEGER** ("user-assigned ID… useful for
recognizing future states"; defaults to 0). ⚠️ **Important:** the doc does NOT
present it as a unique/idempotency key — for CancelOrder the doc explicitly says
"the Client Order ID may not be unique." Therefore **do NOT rely on NDAX
`ClientOrderId` for cross-process duplicate protection**; our persist-before-
submit OrderStore + reconcile-before-retry remain the source of duplicate
protection. Our adapter forwards a numeric `ClientOrderId` only when the caller
wants NDAX-side recognition; otherwise it sends 0.

⚠️ **Key-size/string ambiguity:** the official Request example uses lowercase
`quantity`, the field table capitalizes it (`Quantity`). We use the example form
(`quantity`) in `toNdaxSendOrderRequest`. This is an UNVERIFIED wire detail that
must be confirmed on a real account before enabling placement.

### CancelOrder — POST (mutation, JSON body) — ✅

**Endpoint:** `POST https://api.ndax.io:8443/AP/CancelOrder` (private, signed).
**Call Type: Synchronous.**

✅ Documented request (v3.3 — `AccountId` added; `OrderId`, `ClientOrderId`,
`AccountId` all **conditionally optional**):

```json
{ "OMSId": 0, "AccountId": 0, "OrderId": 0, "ClientOrderId": 0 }
```

The doc says OMS ID + Order ID precisely identify the order (Order ID unique
across an OMS); if you give OMS ID + Account ID you must also give at least the
Client Order ID (Client Order ID alone is not unique).

✅ Documented response = generic `{ result, errormsg, errorcode, detail }` and
**only confirms the call was RECEIVED, not that the order was canceled.** The doc
is explicit: "To verify that an order has been canceled, call **GetOrderStatus**
or **GetOpenOrders**." → `CancelResult.acknowledged` reflects receipt and
`orderStatus` stays `null`; confirmation is a reconciliation step.

### GetOrderStatus — POST? — ⚠️ method ambiguity

✅ Documented request `{ omsId, accountId, orderId }` and response (a single
order object array; the "New" response shape shown in §"Revised calls"). The
doc's response example uses capitalized keys (`OrderId`, `OrderState`, …) with
`OrderState` as a **string** ("Working"/"Rejected"/"Canceled"/"Expired"/"Fully
Executed") and `Side`/`OrderType` as strings.

⚠️ The apidoc does not state an HTTP verb for `GetOrderStatus`, and lists it only
as a User-category WS call in the function index. CCXT exposes it as a **GET**
private read (`privateGetGetOrderStatus`). We treat it as GET (matches CCXT),
isolated in the adapter — flag to confirm against the live API.

### Map to our adapter

`src/exchanges/ndax/orderMappings.ts` encodes the above (pure + unit tested):
`toNdaxSendOrderRequest`, `toNdaxCancelOrderRequest`, `mapSendOrderResponse`,
`mapCancelOrderResponse`, plus enum mappers. These are **not** wired to any live
path while `supportsOrderPlacement=false`; they are the reviewed isolation layer
required before enabling.

- **OrderState**: 🔎 RESOLVED — REST returns **string** values: `"Accepted"`,
  `"Rejected"`, `"Working"`, `"Canceled"`, `"Expired"`, `"FullyExecuted"`
  (CCXT `parseOrderStatus`; numeric enums 0–5 apply to WS payloads only). The
  adapter maps both forms. `Side`/`OrderType` are likewise strings on the wire
  (e.g. `"Buy"`, `"Limit"`). `ReceiveTime`/`LastUpdatedTime` are epoch-ms
  integers; `ClientOrderId` is an integer (0 when unset).

## 7. Fees ✅

Official `ndax.io/fees` (2026): **flat 0.20%** trading fee on every buy/sell —
no volume tiers, **no maker/taker split**. Note: the AlphaPoint `GetOrderFee`
endpoint supports a `makerTaker` parameter, so the platform supports the concept,
but the retail published fee is flat 0.20%. Withdrawal/deposit fees are separate
and not part of trading.

## 8. Rate limits ⚠️ AMBIGUOUS

Sources disagree (likely different API surfaces):

| Source | Limit |
| --- | --- |
| NDAX support "API comprehensive guide" | 50 requests/min REST; 10 subscriptions/connection WS |
| NDAX "API Policy" (legal) | 1000 calls/hour per OAuth token |
| CCXT connector | `rateLimit` = 1000 ms (≈60 req/min, all HTTP), 500 msg/60s WS, 50 msg/60s WS auth |

⚠️ Sources disagree. Action taken (Phase 4): the REST client enforces a
**1 request/second minimum spacing** (matches CCXT's `rateLimit`, the most
restrictive of the credible limits) — `throttleMs` default 1000 ms.

## 9. Error responses ✅

Generic wrapper used by many calls:

```json
{ "result": true, "errormsg": "", "errorcode": 0, "detail": "" }
```

Error codes: **20** Not Authorized, **100** Invalid Response, **101** Operation
Failed, **102** Server Error, **104** Resource Not Found, (+ **106** Operation
Not Supported on some calls).

⚠️ Note: `result:true` only means the call was *received*, not that the action
succeeded. Always reconcile via GetOrderStatus/GetOpenOrders.

## 10. API key permissions / IP restrictions

- ✅ API keys are created in the NDAX account UI with selectable permissions
  (trading, withdraw, etc.) — per ndax.io support pages.
- ⚠️ **IP whitelisting** is supported (per SignalBee troubleshooting: HTTP 403
  "IP restriction blocking request"), but not documented in official NDAX API
  docs. Needs verification / user awareness.

## 11. Sandbox / testnet ❌ / ⚠️

- ❌ **No official public testnet is documented** for the retail platform (re-
  confirmed 2026-08-29: apidoc.ndax.io and ndax.io support pages offer no
  sandbox/testnet for spot order placement; the help center only advises testing
  "in a development environment" — with no such environment provided).
- ⚠️ A third-party host `https://ndaxmarginstaging.cdnhop.net:8443/AP/` is used
  by CCXT/Hummingbot as a "testnet", and SignalBee states "NDAX does not offer a
  public testnet for spot trading." These conflict. **Needs verification with
  NDAX directly.** Because it is third-party and unverified, it is NOT used for
  order-placement validation. There is no known safe non-production mechanism to
  place real SendOrder/CancelOrder calls without risking funds.

## 12. Symbol format & base/quote

- ✅ NDAX instruments use `symbol` = BASE+QUOTE (e.g. `BTCCAD`, `BTCUSD`) with
  separate `product1Symbol` (base, e.g. `BTC`) and `product2Symbol` (quote, e.g.
  `CAD`). Our canonical form is `BASE/QUOTE` (`BTC/CAD`) which the adapter maps to
  NDAX's `BTCCAD` + numeric `InstrumentId`.
- ✅ All instrument-specific calls require numeric `InstrumentId` (same as
  `ProductPairCode`); `OMSId` = 1 throughout.

## 13. Minimum order quantities

- ⚠️ Not in the apidoc GetInstruments sample. Live data (per CCXT) includes
  `MinimumQuantity` / `MinimumPrice`. NDAX FAQ: minimum trade is ~**$1–5 CAD**
  depending on the coin. Needs verification from `GetInstruments` response.

## 14. Precision & tick sizes

- ✅ `GetInstruments` provides `quantityIncrement` and `priceIncrement` (tick
  sizes). `GetProducts.decimalPlaces` (max 8) gives asset precision.
- 🔎 Real-world values: `quantityIncrement` = `0.00000001` and `priceIncrement`
  = `0.01` for BTC/CAD (CCXT sample), with values up to 8 decimals → fits the
  adapter's scale-8 `Money`. Increments arrive as long decimal strings
  (`"0.0000000100000000000000000000"`) parsed via `scaledStrToMoney`.

## 15. Fees — discrepancy to keep in mind

- ✅ Official retail `ndax.io/fees` (2026): **flat 0.20%** on every trade, no
  maker/taker split.
- 🔎 CCXT hard-codes `fees.trading = { maker: 0.002, taker: 0.0025 }`.
  The CCXT fees appear stale/aspirational. **Keep flat 0.20%** (current official
  page is the more recent source). This matters for paper-trade fee simulation:<br>
  good → `feeInfo = { maker: 0.002, taker: 0.002 }`.

### What is required before `supportsOrderPlacement` can safely become `true`

The safe-enablement checklist (each item is currently NOT satisfied):

1. **Live, read-only auth validated** against a real NDAX account: header signing
   (`Nonce`/`APIKey`/`Signature`/`UserId`) accepted for private reads
   (`GetUserAccounts`, `GetAccountPositions`, `GetOpenOrders`), so we can read
   balances/open orders to satisfy the LiveOrderEngine's balance + reconcile
   gates. Uses `ENABLE_AUTHENTICATED_READS=true` via `npm run verify:ndax`.
2. **An explicitly safe, non-production mechanism for placement** — an official
   testnet/sandbox or an explicit paper/demo key that NDAX confirms cannot move
   funds. **No such mechanism has been found. Until one exists, SendOrder and
   CancelOrder must NOT be exercised**, because they would place real orders with
   real funds.
3. **SendOrder/CancelOrder request + response empirically verified** on that safe
   mechanism: exact key casing (`quantity`), whether NDAX accepts a market order
   without `LimitPrice`, `ClientOrderId` numeric acceptance, and that
   `GetOrderStatus`/`GetOpenOrders` return the new order by `OrderId` and by
   `ClientOrderId`. This confirms the `toNdaxSendOrderRequest`/
   `toNdaxCancelOrderRequest`/`mapSendOrderResponse`/`mapCancelOrderResponse`
   mappers and their enums.
4. **Order-lifecycle confirmed**: after an ack (`status:"Accepted"`) the order
   appears via `GetOrderStatus`/`GetOpenOrders`; after `CancelOrder` the canceled
   state is observable there; async ack semantics understood (SendOrder is
   ASYNCHRONOUS — ack ≠ on-book).
5. **IP allow-listing / API-key trading permission** confirmed (the key must have
   `Trading` permission and any IP whitelist must include the bot's egress IP).
6. **Fees confirmed** to use in risk/paper modeling (flat 0.20%).

Until all six are satisfied, NDAX keeps `supportsOrderPlacement=false` and the
adapter's `placeOrder`/`cancelOrder` throw `OrderRejectedError` — live mode fails
closed (the `LiveOrderEngine` refuses to start). The uncertainty stays isolated
behind the adapter; no endpoint, request field, auth header, or order semantic is
guessed into the codebase. The pure order mappers in
`src/exchanges/ndax/orderMappings.ts` are ready to be wired once items 1–6 are
verified, and are covered by unit tests using deterministic fixtures.

### V1 software readiness vs NDAX private-API verification vs live-trading authorization

These three are deliberately distinct and each is a separate gate. Satisfying
one does NOT satisfy the others.

1. **V1 software readiness (this repo).** The code that would drive live
   placement is complete and unit-tested: the `LiveOrderEngine` risk-gates every
   placement through `RiskManager`, persists before submit, never auto-retries an
   ambiguous outcome, and fail-closes on reconcile balance mismatches and stale
   data. This proves the *software* is safe to reason about, but it never touches
   a real account. Fulfilled at the V1 milestone.
2. **NDAX private API verification.** The read and (future) order-path code is
   exercised against a *real* NDAX account whose credentials the owner provisions
   and authorizes. This is the slowest, environment-dependent phase (IP
   allow-listing, key Trading permission, validating header signing for reads,
   then empirically validating `SendOrder`/`CancelOrder` semantics on a
   non-production key as described above). It requires the owner to act; the repo
   cannot do it on its own. NOT fulfilled.
3. **Live-trading authorization.** The human owner gives explicit, deliberate
   approval to place orders that move real funds (in addition to
   `supportsOrderPlacement=true` and the config `realFundsAtRisk=true`
   acknowledgement). This is a people/process gate, not a code gate, and is the
   final authority. NEVER fulfilled.

Point 2 is a prerequisite for the `supportsOrderPlacement` flag to be armed;
point 3 is what actually authorizes moving funds. Until point 2 passes, point 3
is moot for NDAX. Code changes may advance point 1; points 2 and 3 await the
owner.
